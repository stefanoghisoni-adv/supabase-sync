# Colonna `net_value` sui prodotti — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** La tabella `products` del merchant porta una colonna `net_value` = `price - cost_per_item`, e ogni riga idonea che finisce su Supabase la ha sempre valorizzata.

## Il design in breve

- `net_value` è **derivato**, mai inserito a mano: si calcola dove si costruisce la riga, cioè in `transformProduct`. Passando di lì, tutti i percorsi di scrittura (bulk, periodica, webhook) lo ottengono senza doverli toccare uno per uno.
- L'arricchimento del costo (`enrichVariantCosts`) avviene **prima** della trasformazione su ogni percorso, quindi al momento del calcolo il costo è già quello vero.
- L'idoneità diventa: riga con costo **e** con `net_value` calcolabile. Così l'invariante richiesta — "un prodotto idoneo ha sempre il profitto compilato" — è garantita dal filtro che decide cosa entra in tabella, non da un vincolo del database.
- La colonna resta **nullable** sullo schema. Un `NOT NULL` sarebbe applicabile solo alle tabelle nuove (su quelle esistenti l'`ALTER ... ADD COLUMN NOT NULL` senza default fallisce se ci sono righe), creando due schemi diversi a seconda di quando il merchant si è collegato. La garanzia sta nel filtro di idoneità, che è uniforme.

## Global Constraints

- **Non toccare** `app/lib/stats/product-readiness.ts` né `api.stats.products`: contano l'idoneità sui dati Shopify (dove il prezzo c'è sempre), non sulle righe Supabase. Restano allineati.
- Arrotondare il risultato a **2 decimali**: la colonna è `NUMERIC(10, 2)` e senza arrotondamento la sottrazione in virgola mobile produce code (`19.90 - 4.35 = 15.549999999999999`).
- `cost_per_item === 0` è un costo esplicito e resta idoneo (vedi il commento in `product-eligibility.ts`): la condizione è sul `null`, non sulla falsità.
- **Non esiste infrastruttura per test di componenti React**: non aggiungerla.
- La suite riporta **293 test** a inizio lavoro. Se ne vedi molti meno il comando è stato interrotto: rilancialo.
- TDD. `npx vitest run`, `npx tsc --noEmit`, `npm run build` verdi a fine di ogni task.

- [ ] **Step 3: Implementa**

In `app/types/shopify.ts`, dentro `SupabaseProductRow`, accanto a `cost_per_item`:

```ts
  cost_per_item: number | null;
  // Profitto per unita': price - cost_per_item. Derivato, mai scritto a mano.
  net_value: number | null;
```

In `app/lib/supabase-schema.ts`, in `PRODUCTS_COLUMNS`, subito dopo la riga di `cost_per_item`:

```ts
  { name: 'net_value', type: 'NUMERIC(10, 2)' },
```

In `app/lib/transformers/product.server.ts`, in cima al file, una funzione unica usata da entrambi i rami (così non si duplica l'arrotondamento):

```ts
// Profitto per unita'. Senza costo non e' calcolabile: null, e la riga risultera'
// non idonea. L'arrotondamento a 2 decimali evita le code della sottrazione in
// virgola mobile (19.90 - 4.35 = 15.549999999999999) prima ancora di arrivare
// alla colonna NUMERIC(10, 2).
function netValue(price: number, cost: number | null): number | null {
  if (cost === null) return null;
  return Math.round((price - cost) * 100) / 100;
}
```

In **entrambi** i rami di `transformProduct`, il costo è oggi calcolato inline
(`cost_per_item: variant.cost ? parseFloat(variant.cost) : null`). Estrailo in una
costante locale prima dell'oggetto restituito, così `net_value` riusa lo stesso
valore invece di ricalcolarlo:

```ts
      const cost = variant.cost ? parseFloat(variant.cost) : null;
      const price = parseFloat(variant.price);
      // ...
      price,
      cost_per_item: cost,
      net_value: netValue(price, cost),
```

Attenzione al ramo con varianti: è un `.map()`, quindi le costanti vanno dentro il
corpo della callback (serve passare da `variant => ({...})` a `variant => { ... return {...} }`).

- [ ] **Step 3: Implementa l'idoneità**

In `app/lib/eligibility/product-eligibility.ts`, estendi la condizione mantenendo il commento esistente e aggiungendo il perché della seconda clausola:

```ts
// ...commento esistente sul cost_per_item...
// La seconda clausola rende vera nei dati la promessa fatta all'utente: un
// prodotto idoneo ha SEMPRE il profitto compilato. Non serve un NOT NULL sulla
// colonna, perche' e' questo filtro a decidere cosa viene scritto su Supabase.
export function isProductRowEligible(row: SupabaseProductRow): boolean {
  return row.cost_per_item !== null && row.net_value !== null;
}
```

- [ ] **Step 4: Allinea anche il salvataggio manuale del costo**

In `app/routes/products.issues.tsx`, l'action scrive oggi solo il costo:

```ts
        .update({ cost_per_item: parsed })
        .eq('shopify_variant_id', variantId);
```

Quel percorso lascerebbe `net_value` fermo al valore vecchio. Il prezzo **non va
preso dal client** (sarebbe manipolabile): leggilo dalla riga già su Supabase e
calcola. Se la riga non esiste — normale, perché finché manca il costo il prodotto
non è idoneo e non viene sincronizzato — non c'è nulla da aggiornare e si esce
senza errore: la sync successiva lo inserirà con il valore giusto.

```ts
      const supabase = createSupabaseClient(shop.supabaseConfig);

      // Il prezzo dalla riga esistente, non dal form: il client non deve poter
      // decidere un valore che finisce in tabella. Se la riga non c'e' ancora
      // (prodotto non idoneo, quindi mai sincronizzato) non si aggiorna nulla.
      const { data: existing, error: readError } = await supabase
        .from(shop.supabaseConfig.tableNameProducts)
        .select('price')
        .eq('shopify_variant_id', variantId)
        .maybeSingle();
      if (readError) throw readError;

      if (existing) {
        const price = Number(existing.price);
        const { error: sbError } = await supabase
          .from(shop.supabaseConfig.tableNameProducts)
          .update({
            cost_per_item: parsed,
            net_value: Math.round((price - parsed) * 100) / 100,
          })
          .eq('shopify_variant_id', variantId);
        if (sbError) throw sbError;
      }
```

Il `catch` esistente resta invariato e copre anche la lettura.

## SQL da eseguire a mano (prima del deploy)

Il DDL gira solo al collegamento del progetto (`api.supabase.select-project.tsx:96`),
quindi le tabelle già create non ricevono la colonna da sole. Sul progetto Supabase
del merchant:

```sql
ALTER TABLE products ADD COLUMN IF NOT EXISTS net_value NUMERIC(10, 2);
```

I merchant che si collegheranno da qui in avanti la ottengono dal `CREATE TABLE`.

## Note di verifica manuale (post-deploy)

- Dopo una sync, su Supabase ogni riga di `products` ha `net_value` valorizzato e pari a `price - cost_per_item`.
